# Audit du projet — Amicale ASP La Madeleine (suite)

Date : 2026-08-13
Périmètre : sécurité, bugs, qualité de code, dépendances, performance, accessibilité — couvre le code ajouté depuis le précédent audit ([AUDIT.md](AUDIT.md), 2026-06-28) : candidatures/quiz de recrutement, notifications push/email, idées, tâches, réunions, votes, module Organisation d'événement, trombinoscope, PWA, SEO, page d'accueil publique.
Non modifié : rien n'a été corrigé automatiquement dans le code, ce document est un état des lieux à trancher.

## Majeur — sécurité

### 1. Injection HTML dans l'email « Nouvelle candidature »
`supabase/functions/send-notification/index.ts`, fonction `corpsEmailCandidature`. Les champs `prenom`, `nom`, `telephone`, `email` de la table `candidatures` sont interpolés tels quels dans le HTML de l'email envoyé aux membres ayant `acces_candidatures`. Or `candidatures` est insérable par **n'importe quel visiteur anonyme** via la policy RLS `candidatures_insert_public` (`WITH CHECK (true)`, migration `20260808000000_candidatures.sql`) — le quiz public ne protège rien côté API.

**Scénario concret** : un visiteur soumet le formulaire avec `prenom = "<a href=\"https://phishing.example\">Cliquez ici</a>"`. L'email reçu par le bureau affiche un lien cliquable arbitraire dans un message qui semble provenir de l'app interne. La plupart des clients mail bloquent le JS mais pas les balises `<a>`/`<img>`/CSS.

**Correctif recommandé** : échapper `<`, `>`, `&`, `"` avant interpolation dans `corpsEmailCandidature` (et par défense en profondeur dans `gabaritEmail`/`send-convocation`, même si ces derniers champs sont bureau-contrôlés).

### 2. RLS `candidatures_insert_public` trop permissive
Même migration. Le `WITH CHECK(true)` laisse un appelant API direct (hors formulaire) fixer lui-même `statut_eligibilite` et `traite` — un candidat pourrait s'auto-déclarer `eligible` ou `traite: true` pour se soustraire au suivi. Impact limité (donnée de suivi interne, pas de fuite de données tierces), mais facile à corriger : restreindre le `WITH CHECK` aux colonnes attendues (`statut_eligibilite` recalculable côté trigger, ou au moins `traite` forcé à `false` à l'insert).

## Majeur — bugs

### 3. Vote multi-questions non transactionnel
`src/pages/votes/Vote.tsx:96-106`. `handleSubmit` insère les réponses question par question dans une boucle, sans transaction. Si l'insertion échoue à la question N (policy RLS, coupure réseau), les questions 1..N-1 restent enregistrées en base mais l'UI affiche l'erreur et ne marque pas `submitted`.

**Scénario concret** : au rechargement suivant, `fetchVote` (L49-52) détecte que `vote_reponses` contient déjà des lignes pour ce membre (`mesRep.length > 0`) et force `submitted = true` → l'écran affiche « Vote enregistré » alors que le vote est en réalité incomplet, et l'utilisateur ne peut plus terminer ni corriger.

**Correctif recommandé** : un seul `insert` avec un tableau de lignes (Supabase le supporte nativement), ou une RPC `SECURITY DEFINER` transactionnelle.

### 4. Détail de vote non anonyme illisible
`src/pages/votes/Vote.tsx:358`, composant `DetailNonAnonyme`. Affiche `r.membre_id` (UUID brut) au lieu du nom du membre — aucune jointure avec `membres`. La fonctionnalité « voir qui a voté quoi » (votes non anonymes) est présente en base mais inexploitable côté UI en l'état.

### 5. Audience de notification « Nouvelle candidature » désynchronisée de l'admin fixe
`supabase/functions/send-notification/index.ts` (requête `membresQuery.eq('acces_candidatures', true)`) vs `src/contexts/AuthContext.tsx:57` (`accesCandidatures = user?.email === ADMIN_EMAIL || membre?.acces_candidatures === true`). Le compte admin fixe voit `/candidatures` dans l'app mais ne reçoit **jamais** de notification push/email pour une nouvelle candidature, sauf si sa ligne `membres` a explicitement `acces_candidatures = true`. C'est une troisième copie de la règle d'accès (après `AuthContext` et les policies RLS) qui a divergé silencieusement — même famille de risque que celle déjà documentée dans CLAUDE.md pour `isAdmin`/`is_bureau_admin`.

## Mineur

- **`ROLES_BUREAU` dupliqué une troisième fois** (`send-notification/index.ts:78`) — déjà dupliqué entre `AuthContext.isAdmin` et la fonction RLS `is_bureau`. Toute évolution des rôles de bureau doit être répercutée dans 3 endroits sans garde-fou de synchronisation.
- **`auth.jwt()->>'email'` partout dans les nouvelles policies RLS** (candidatures, evenement_organisation/stands/deadlines/affectations, votes\*, idees, taches, reunions\*, push_subscriptions), jamais `auth.uid()`/`membres.auth_user_id`. Cohérent avec l'existant pré-audit, pas une régression, mais c'est une dette systémique à garder en tête si un jour un membre peut changer son propre email.
- **`design-system/` (non tracké par git)** : dossier entier (tokens CSS, préréglage Tailwind, thème « caserne1847 ») non référencé nulle part dans `src/`, `tailwind.config.cjs` ni `vite.config.ts`. Expérimentation de refonte jamais branchée — à intégrer ou supprimer, sinon elle restera invisible (untracked) et sera oubliée.
- **`scripts/generate-qr-code.mjs`** : bien câblé (`npm run qr`, dépendance `qrcode` déclarée), mais écrit ses sorties (`qr-codes/`, `recrutement_blanc*.png`) à la racine du repo sans entrée `.gitignore` — risque de commit accidentel d'assets binaires générés.
- **Aucun `<label>` associé aux champs de formulaire** sur la majorité des pages avec `<input>` (Recrutement, MonCompte, Calendrier, Membres, Documents, Organisation, Votes, Réunions, Tâches, Idées, Login) — uniquement des `placeholder`. Accessibilité lecteur d'écran dégradée ; déjà signalé comme non couvert dans l'audit précédent, toujours vrai et désormais sur un périmètre plus large.
- **Aucun code-splitting par route** (`src/App.tsx` importe toutes les pages statiquement). Le build produit un unique chunk JS de **551 kB** (145 kB gzip) — chargé intégralement même par un visiteur anonyme atterrissant sur `/` (Welcome) ou `/recrutement`, alors que ces pages n'ont besoin ni du code de Dashboard/Membres/Cotisations/Organisation ni de la lib QR/ICS. `React.lazy` + `<Suspense>` par route réduirait significativement le TTI sur mobile.

## Dépendances

- `npm audit` : **2 vulnérabilités modérées** sur `react-router-dom`/`react-router` (open redirect via backslash dans `<Link>`/`useNavigate`, CVE-2025-68470-bypass ; constructor injection dans `deserializeErrors()` côté SSR — non exploitable ici car pas de SSR, mais la partie open-redirect s'applique). Correctif disponible via `npm audit fix` (reste en 6.x, pas de breaking change majeur a priori — à vérifier après upgrade).
- `npm outdated` : rien de critique. `react`/`react-dom` 18.3.1 → 19.x et `react-router-dom` 6.30 → 7.x disponibles mais ce sont des majors (migration à planifier, pas un correctif de routine). `@supabase/supabase-js` 2.108 → 2.112 (mineur, sans risque).

## Build / lint

- `npm run build` : ✅ passe (voir avertissement bundle size ci-dessus).
- `npm run lint` : ✅ propre, aucun warning.
- `tsconfig.json`/`tsconfig.node.json` (modifiés récemment, non commités) : `moduleResolution NodeNext → Bundler` cohérent avec Vite ; `tsconfig.node.json` gagne `composite: true` et perd `noEmit: true`, combinaison correcte pour les projets TS référencés. Pas de régression.

## Points vérifiés et sains (pas de nouveau problème)

- RLS activé avec policies cohérentes sur toutes les tables ajoutées depuis le dernier audit (candidatures, evenement_organisation, stands, deadlines, affectations, votes\*, idees, taches, reunions\*, push_subscriptions), y compris scoping strict de `push_subscriptions` par membre.
- Trigger `lock_sensitive_membre_fields` correctement étendu à `acces_candidatures`.
- Les 4 edge functions (`create-membre-access`, `send-convocation`, `send-notification`, `_shared/resend.ts`) : authentification correcte (RPC de rôle ou `x-webhook-secret`), pas de secret en dur, pas de clé service-role exposée côté client.
- `RequireAuth` bien appliqué à toutes les routes protégées dans `App.tsx` (dashboard, membres, documents, cotisations, calendrier, mon-compte, votes, idées, tâches, réunions, candidatures) ; aucune page orpheline non routée.

## Non couvert par cet audit

- Revue manuelle fine des policies RLS des tables du module Organisation (cas d'usage métier détaillés stand par stand).
- Tests d'accessibilité automatisés (axe/Lighthouse) — l'absence de `<label>` a été repérée par lecture de code, pas par un outil dédié.
- Performance runtime réelle (Lighthouse mobile) — seule la taille du bundle a été mesurée.
- Configuration Supabase/Netlify réelle (buckets Storage, redirect URLs, secrets déployés) — non vérifiable depuis le repo.
